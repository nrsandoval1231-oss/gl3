# A5 bounded browse architecture — 2026-10-07

**Measured problem.** On the restored, isolated `gl3audit_corpus_test` copy, unchanged baseline `opportunity_projection(tier="Signal")` returned 1,167 rows after 4,719 SQL statements, 7.364 seconds cold-process elapsed and 56,156,469 bytes peak Python allocation. Raw read-only script/report: `.artifacts/audit-20261007/benchmark-baseline.py` and `baseline-loading-measurement.json`. These are one-run local measurements, not production latency. `/api/opportunities` returns the full list. `_commercial_triage_cards(session, 50)` calls that full projection before taking 50 grouped cards. `/api/commercial/triage/history` loads all Pursuit snapshots, all versions and all notes then sorts/filters in Python. Web loads all opportunities on entry and filters locally.

**Decision.** Keep canonical admission/qualification and `work_identity()`/`cards()` semantics as the authority. Split reads into a bounded **candidate-summary stream** and **selected-page hydration**. The query may push down filters only when those fields are already authoritative; never use stored `PowerNeed.tier`/MW alone as effective qualification. In bounded batches, run the *canonical* current-support and effective-qualification rules, including accepted evidence-version/hash and project/activity binding, admission/floor rules, source conflicts and research-state veto. An unsupported or conflicting need cannot become a page candidate merely because a stored tier or broad SQL text match says it can. Existing canonical evaluators may currently query per need/project; allow narrow preload or batch-input seams in `ingestion/service.py`, `intelligence/project_state.py`, and `intelligence/buying_chain.py` so they consume the same preloaded data and policy. Do not copy or simplify their rules. Measure statement growth across batches.

The compact summary still needs **all inputs that affect browse identity/order**: need/project IDs, `PowerNeed.updated_at`, location/site and activity; current accepted supporting Evidence title/abstract, source ID, external/document number and exact content/version; lifecycle state and relevant lifecycle events; research conflict/veto and display decision; and **all retained evidence dates** used by `_priority()`. Do not discard old dates merely because full historical excerpts are deferred: priority currently takes the maximum across `item.evidence`, including retained versions. The first supporting evidence used by `cards()`/`work_identity()` follows the existing `Evidence.observed_at DESC, Evidence.content_hash DESC` ordering; a different lateral/latest shortcut can change group identity. This summary is intentionally richer than one evidence ID but must exclude full excerpts/history payloads and remain batch-bounded in memory. Compare every derived `_priority()` tuple and work key to the baseline on a frozen corpus.

Count and order the same eligible set before page slicing. Group by the exact `work_identity(source_id, external_id, site)` key before slicing so related needs are never split across pages. Preserve `cards()` ordering: sort candidates by `_priority()` and card ID; group insertion/order follows **first priority encounter**, while the group's representative is the card with **minimum ID**. A group's conflicting sibling state may change its disposition after merge; count grouped dispositions after that merge, not before it. Use the same canonical grouping seam in A1-R1's all-active planner and A5, with visible UI limit applied only after grouping. Do not add a second grouping algorithm. If an index/cache becomes necessary, maintain it transactionally from canonical evaluation with explicit invalidation/backfill and parity proof; otherwise stream bounded summaries and keep only required sort/group metadata. No second tier or evidence-admission policy for speed.

Hydrate only selected group members with full evidence, lifecycle, buying chain, notes and research detail, using bulk `IN` reads. Fetch complete evidence/history separately when detail is opened. Keep **two route orders distinct**: `/api/opportunities` currently orders supported needs by `PowerNeed.updated_at DESC` (add a stable ID tie-break for paging); commercial triage uses the canonical priority/group order above. A single shared ordering would be a behavior regression. Use server bounds (e.g. page size 1–50 for opportunities/triage, 1–50 for saved history) and stable offset/keyset navigation. Publish an **all-eligible grouped total** for navigation separately from triage disposition counts. Existing triage disposition/cohort counts describe the **selected first 50 grouped cards**; retain that page-scoped meaning on each selected page, including after sibling-state merging, instead of silently converting them to all-eligible totals. `Signal` display counts remain record counts; label each scope explicitly. Missing/unknown values stay selectable and visible, never coerced to zero. Keep old route identities and authorized response fields; additive page metadata is acceptable, and generated contracts/client calls must migrate together. If the old list response must remain for compatibility, cap it with explicit pagination parameters and document the changed default—never keep a hidden unbounded route.

**Sequencing.** A5a: measure and implement candidate+group page projection with parity tests against prechange output on small and retained-corpus snapshots; scope SQL predicates. A5b: page opportunities, triage and saved history; on-demand detail/evidence; generated OpenAPI and client updates. A7 uses these APIs. A6 factual corrections must use the same invalidation/bulk support seam if one is introduced. A1 scheduler must retain access to *all* supported active unsaved needs and may not depend on the visible page.

**Acceptance.** Compare every eligible need, exact work key, priority tuple, group representative, group order/disposition and opportunities updated-at order on a frozen corpus before/after. Compare page-scoped disposition counts after merged-sibling state resolution and separate all-eligible grouped totals across filters and page concatenation, especially same-work BP/EP siblings, conflicting need states, older retained evidence dates, nonmatched/unknown geography, and metadata-only snapshots. Test A→B→A evidence reversion, accepted-source conflict/research veto and below-floor qualification so a compact read never promotes an unsupported candidate. Full-page detail must still show exact source URLs, evidence IDs/hashes and historical versions. On the same frozen 1,167-need corpus, target **at most 200 SQL statements for a 50-card read**, with no per-need/project linear statement growth; compare cold elapsed and Python peak allocation against the measured 4,719 statements/7.364 seconds/56,156,469 bytes and require improvement in both. Measure warm latency and response bytes too. This is a local regression target, not a production SLO; semantic parity remains a hard gate even if the target is met. Report actual deltas and limitations, and preserve replay idempotency and existing protected UI behavior.
