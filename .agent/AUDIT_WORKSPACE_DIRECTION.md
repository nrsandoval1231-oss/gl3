# Audit workspace direction — 2026-10-20

Status: architecture direction only; not implementation acceptance. Baseline `9e9e188bdf2825a8305a0e9eac0b23f0af1df47e`. Governed by PRD requirements 11, 26, 32–34, the October 18 UI canon, Finish Contract, and audit F05/F08/R01. No new Tribunal or platform rewrite.

## Decision

After the controller independently reruns `AUDIT-CORE` on its exact terminal SHA and accepts its bounded gates, issue one `AUDIT-WORKSPACE` Luna packet in a new descendant of that SHA. `AUDIT-RETAINED` may continue concurrently in its exclusive worktree because it owns no API app, models, migrations, or web files. Keep the current server-backed need table and compact briefing. Add a bounded authenticated morning-change read and an explicit persisted “mark reviewed” action. Derive source changes from retained `ChangeEvent` transitions and operator fact changes from the immutable `CallFactDecision` journal; never generate discoveries from a successful source recheck or `PowerNeed.updated_at` alone. Source-health exceptions come from the existing health assessment and retain their own status/clock semantics.

`ChangeEvent` is project scoped. `power_need_changed` has before/after arrays keyed by activity, while `PowerNeed` has a unique `(project_id, activity_key)` and persists after closure. Resolve changed activities to stable need IDs through that key, including inactive rows. Classify an added active activity as discovered, Signal-to-Prospect/Lead as promoted, a prior active activity missing/inactive afterward as closed, and other supported semantic changes as changed. Preserve the event ID, detection time, source date, exact evidence or buying-chain source links, prior/new facts, and project/need target. Do not call an initial project baseline or a raw `discovered` event a need discovery unless its accepted need association is verified through retained observation/need links. Project-only phase/buyer events may be shown with an honest project target; never arbitrarily assign them to one sibling need. Snapshot-absence events mean source-listing review, not a closed need. If existing retained events cannot support a category, report it unavailable and add only the minimal canonical event capture required for future transitions, with replay proof.

F08 operator gap: `decide_need_call_fact` persists a `CallFactDecision` and requalifies the need without writing `ChangeEvent`. Include accepted, corrected and retracted **decision** receipts as `changed` items only when the decision changes that fact version's accepted assertion; exclude draft creation, rejected drafts and the internal `superseded` companion receipt of a correction. Key and link each item to its exact `need_id` and `fact_version_id`, actor, decision time, reason and authenticated `/api/needs/{need_id}/facts` history. For accepted, display “previously unaccepted version” to the accepted value; for corrected, predecessor version value to corrected version value; for a retraction of an accepted version, accepted value to “retracted.” These are version-level before/after values, **not** a claim that the need had no other accepted or conflicting facts. Preserve the reporter/source-reference attribution as an operator report; never cite the original permit Evidence as support for the call. Do not infer a promotion, closure or historical tier before/after from a journal item. If the before/after version state or valid correction predecessor cannot be reconstructed, present unresolved history rather than inventing a value.

Persist a singleton operator review baseline (`reviewed_at`, `last_token`, prior receipt count, actor/source if available) and an additive acknowledgment table keyed by a typed immutable text identity: `change:<ChangeEvent.id>` or `fact:<CallFactDecision.id>`. Two tables still suffice; the acknowledgment key is not a polymorphic foreign key, so derive/validate every eligible key from its canonical journal and keep a type/format constraint. First use must say “since tracking began” (bounded recent items and full unreviewed count) until an explicit review; it must not silently mark history reviewed. Use the journal event, not a derived need subrow, as the acknowledgment unit: one `ChangeEvent` that changes several sibling needs is one digest item with all affected need links, so acknowledging the item cannot hide a second undisplayed sibling item.

Review protocol: authenticated GET in one repeatable-read snapshot computes category counts over the complete eligible **unacknowledged** event set from both journals, then returns at most 50 items ordered by `(created_at DESC, typed_key DESC)`, plus total/`has_more`, source-health exceptions and a SHA256 token over the ordered displayed typed keys and the page's defined projection/version. GET writes nothing. The UI action is explicitly **“Mark these displayed changes reviewed”** and is disabled for an empty page. Authenticated same-origin POST receives only that token. In a fresh repeatable-read transaction, acquire/initialize the singleton baseline row lock first, then recompute the current first page and token under the same snapshot. If the token differs, return 409 and fetch a new briefing. If it matches, insert acknowledgments for exactly those at-most-50 typed keys (`ON CONFLICT DO NOTHING`) and update the baseline's `reviewed_at`, `last_token` and receipt count in that transaction. A replay of `last_token` returns its prior 200 receipt without acknowledging any new events; a concurrent baseline serialization failure gets a bounded retry or 409. A later-committing event is never acknowledged simply because its ID or timestamp precedes the displayed page; it remains unreviewed. A new commit that changes the current page before POST forces 409; one outside the displayed page remains unreviewed after the POST. Page through remaining events. A full-set digest plus bulk acknowledgment would turn a compact briefing action into an unbounded database read/write transaction, so it is excluded.

A scalar max-ID or timestamp cutoff is unsafe because an earlier allocated event may commit after a later event is reviewed. Keep filters on the opportunity table independent of global briefing counts, and label units/scope. A digest item links directly to `/?view=workspace&need=<id>` when a need exists, including closed need detail/history; otherwise to supported project history. If a closed need detail route currently requires active browse membership, add a narrow authenticated historical read rather than resurrecting it in active browse. Source-health exceptions are read separately and are not cleared by change-event review.

F05: associate each successful `WorkspacePage` with its normalized request identity (filters, sort, offset, cohort). While a new request is loading or fails, hide old table rows and counts unless visibly labelled with their original filter set and disabled cohort actions. Keep current controls, explicit retry and error. An off-page detail may remain only if clearly separate from the failed current list; reset stale commercial preview. Abort/sequence guards still reject late responses. Do not clear persisted canonical data.

## Packet boundary and proof

Owner: one Luna from the exact controller-validated CORE terminal SHA, in a separate descendant checkout; record that SHA in the packet. Allowed surfaces: `web/src/features/workspace/Workspace.tsx`, its focused web tests and API client/generated types; a new focused backend morning projection, one additive migration/model change creating exactly the baseline and acknowledgment tables, and a narrowly scoped authenticated API endpoint in `backend/src/gridlens/api/app.py` after CORE releases that file. Changes to `change_detection.py` or ingestion event creation require a separate explicit packet if accepted retained events prove insufficient. Exclude CORE's ranking/correction/limiter/decision/queue changes, RETAINED's ingestion/news/buying-chain changes, qualification rules, brand assets, deployment, and production data. Do not cherry-pick either builder into the integration checkout until both terminal handoffs and independent bounded validation. Integrate serially in dependency-safe order, then run combined affected and full exact-candidate gates; resolve API/migration ownership against that final joined SHA.

Acceptance: PostgreSQL tests for discovery/promotion/material change/closure of sibling needs, one multi-need source event as one acknowledged item, accepted/corrected/retracted operator facts as typed `changed` items with exact need and local history links, independent conflicting reports, no draft/rejected/superseded duplicate, and no fabricated tier/source attribution; correction/replay idempotence, unchanged refresh, snapshot-absence semantics, evidence links and dates, first-use/unreviewed/mark-displayed/concurrent-event behavior across both journals, token mismatch 409, exact replay receipt, late earlier-key commit remaining unreviewed, auth/same-origin denial, 50-item cap versus full counts, failed/pending health states, and closed need navigation. Browser tests at desktop/mobile cover F05 filter failure and late response, loaded/empty/error/pending briefing, each category link, review persistence across reload, 409 refresh, remaining-pages wording, and Back/filter restoration. Run affected Ruff/mypy/backend tests, generated-type check, frontend typecheck/build/browser tests, migration upgrade and drift checks, then frozen exact-candidate gates and independent Sol review under the Finish Contract. Fixture proof is not live-source or deployment proof.

## R01 measurement gate

Before changing publication storage, benchmark disposable PostgreSQL copies at (a) current retained corpus scale and (b) a documented larger fixture scale. Record database/version/config, corpus size, row counts, generated fixture provenance, candidate SHA, concurrency and warmup. Repeat single-fact operator saves, bounded batch ingestion, and clock rollover with an idle and competing-reader condition. Capture p50/p95/p99 end-to-end write and list/detail/filter reads, publication lock wait/hold, rows copied and rebuilt, WAL bytes, ANALYZE/group/prune time, pending-generation duration and 5xx/pending counts; use database timing/logs and `pg_stat_*` or explicit counters, with before/after samples and raw receipts. Separate scoped refresh from full rebuild, and never run a synthetic benchmark against production. First check whether the measured defect is per-record publication frequency, corpus copy volume, or query behavior. Optimize only a reproduced bottleneck with a bounded packet and regression proof of atomic freshness, coherent cohort pagination, crash recovery and unchanged replay. Proposed <=1 s p95 list/detail target in the audit is a target, not an observed SLO.

## Risks and next direction

The existing `/api/changes` is Chicago-today/project-title oriented and may dereference missing evidence; it is insufficient as the new digest contract. Initial material-state snapshots may omit a first-need transition; verify retained creation cases before promising discovered counts. `created_at` is detection time, not publication or occurrence time. Global counts must not inherit a filtered 25-row page. Review watermark migration must be additive and preserve existing history. Full-row copy occurs inside the singleton publication fence, but production latency is unmeasured.

Direction: `CONTINUE`: independently validate CORE's terminal SHA, then dispatch the single `AUDIT-WORKSPACE` packet on its descendant while RETAINED finishes in exclusive files. Wait for both terminal handoffs, validate each, serially integrate, and run combined exact-candidate gates and independent review. R01 has its separately measured direction in `AUDIT_PUBLICATION_DIRECTION.md`. Completion remains governed by the Finish Contract.
