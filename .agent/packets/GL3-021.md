# GL3-021 — Project matching performance (proposed next slice)

Measured frontier: the GL3-020 RRC first ingest scans all existing projects for each new permit and repeatedly classifies the same incoming observation inside the candidate loop. This is a CPU/scaling limitation, not grounds to weaken evidence or identity rules.

Bounded direction: cache pure observation-level classification and normalization within each matching pass; retain deterministic match decisions, conflicting geography/type handling, aliases, same-site/facility logic, separate upstream/fixed O&G assets and ambiguity. Consider narrower candidate queries only with proof they preserve every supported match and recorded decision. No new source, schema, queue, provider or qualification policy by default.

Acceptance: compare project/need identities and full matching decisions on retained real Austin/Chicago/Georgia/RRC inputs before and after; exercise same-name/different-site and conflicting-asset regressions; measure runtime at increasing candidate counts; preserve replay/evidence/tier behavior. Use an isolated validation database for comparative runs and preserve the now-populated runtime. Independent review required. This packet is proposed work, not implemented capability or launch completion.
