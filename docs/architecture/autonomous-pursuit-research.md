# Autonomous pursuit research — implementation reconstruction

Inspection baseline: remote `main`, `6c8bdf3e3163adde078f8543d43c0256bc11eb82`,
verified October 4, 2026. This document records the design before implementation;
it is not a completion, deployment, or production-validation claim.

## Existing behavior

1. Pursuits are generated by `domain/commercial_triage.py` from admitted active
   Signal needs exposed by the existing opportunity projection. Exact-event
   siblings can share a review card while retaining separate Project/PowerNeed
   identities. `api/app.py` persists immutable meaningful evaluation versions in
   the existing Pursuit snapshot. Read-only projections do not create receipts.
2. RESEARCH blockers are at most two selected missing-fact strings. The current
   `next_question` can combine several unknowns; it is not a durable independently
   scheduled question. Holds and evidence conflicts also produce RESEARCH.
3. `power_need_brief` jobs interpret retained evidence only, choose from curated
   fact IDs, enforce pre-request daily reservations, fence writes, and retain
   prior brief versions. One mutable brief per need and indefinite same-input
   caching cannot represent two independently retried research questions.
   The older `pursuit_research` job retrieves bounded official Austin/RRC/city
   evidence and saves PursuitDocument/PursuitResearchRun receipts. It does not
   admit those documents into the canonical evidence graph.
4. Canonical ingestion retains Source → Observation → immutable Evidence.
   Accepted Interpretation versions bind evidence hash, physical project and
   activity; NeedObservation links and deterministic admission control visibility.
   News can supplement an already supported same-project/same-activity need.
   Buying-chain enrichment separately preserves immutable document and relation
   versions, distinguishing organization involvement, employment, personal project
   assignment, contacts and authority. Neither a research document nor a model
   response alone is an accepted canonical fact.
5. Commercial reevaluation currently runs on explicit authenticated evaluation.
   Changed input/disposition appends a saved card version; unchanged replay
   preserves receipt timestamps and daily counters. Research does not currently
   close this loop. The commercial evaluator never writes evidence tiers.
6. Reuse unchanged: PostgreSQL jobs and fencing, source adapters, public URL
   validation and DNS-pinned retrieval, immutable evidence identity, conservative
   matching/admission, existing buying-chain semantics, project-state projection,
   deterministic triage rules, same-origin authenticated actions, UI disclosure
   patterns, and zero-authority EvidenceJudge. Preserve existing qualification;
   unsupported Prospect/Lead outcomes must remain unavailable.
7. Minimal new capability: durable single-question attempts attached to an existing
   pursuit/need/project; deterministic blocker planning and ordered routing;
   bounded retained-first acquisition; canonical admission through existing
   services; and automatic calls to the same commercial evaluation/receipt service.

## Implementation plan

- Extract receipt persistence for shared API/worker use without changing triage.
- Add one question table with immutable input context, project/need/pursuit keys,
  status, fingerprints, budget, attempt/result receipts and retry/follow-up state.
  Reuse Job.target_id; lock the pursuit to cap active blockers at two. Existing
  source-wide enqueue deduplication cannot be used for independent targets.
- Plan exact questions deterministically and search retained evidence first.
  Prefer registered structured sources, then bounded public URLs, then configured
  Firecrawl discovery. Provider absence and unsupported extraction stay visible.
- Persist acquired documents through canonical evidence services and use current
  matching/admission before any accepted-state change. Reuse buying-chain
  enrichment for relations; never create personal assignment or authority from
  employment. Research workers never assign pursuit state or tiers.
- Persist per-question pre-I/O debits, source checks, accepted/rejected evidence,
  unresolved results, exact reevaluation receipts and at most one follow-up.
  Include source-specific freshness, semantic state/evidence fingerprints, URL
  and document deduplication, and explicit operator refresh.
- Expose question progress and prior/new pursuit versions within the current UI.
  Validate adversarial boundaries, migration preservation, replay, browser flows
  and the actual retained PR23 corpus before PR delivery.

## Independent design review

A separate read-only reviewer confirmed the design and flagged target-blind
enqueue deduplication, canonical admission bypass risk, indefinite brief caching,
and the need for pre-I/O reservations and fenced writes. Arbitrary URLs must use
the existing DNS-pinned public reader; byte limits alone do not prevent SSRF.

## Implemented candidate and boundaries

The implementation now has `PursuitResearchQuestion`, migration `0014`,
`pursuit_question` target jobs, startup/hourly planning, authenticated scheduling,
budget reservations, source caches, retained-only buying-chain projection, exact
Austin/Chicago/Seattle/Boston/El Paso/Federal Register exact-record GET refresh
through canonical ingestion, eligible retained public URL retrieval, optional
URL-only Firecrawl discovery and bounded public-page extraction, and shared commercial
reevaluation. UI preserves question context, source receipts and before/after state.
Read-only `scripts/pursuit_research_metrics.py` summarizes receipt outcomes and
unknown costs without generating work.

Question fingerprints include policy, question, queries and source preferences.
Evidence fingerprints include the commercial semantic input hash and project
identity. Reuse requires freshness, unchanged source version and current canonical
support. Explicit refresh bypasses this cache. Acquisition uses nonblocking advisory
locks: a competing retrieval yields an explicit unresolved limitation rather than
waiting outside the question deadline or duplicating requests. Pre-request receipts
retain uncertain interrupted requests; exhausted leases terminalize visible failures.
Follow-up questions cannot themselves create children. PARTIALLY_RESOLVED requires
new canonical answers to components of the exact question; accepting unrelated
project evidence does not count as progress on that blocker.

Retained-first replay precedes external acquisition. Existing canonical facts remain
usable without fetching. Reinterpretation of a retained public document additionally
requires its original accepted Source/Observation/Interpretation/Evidence identity,
matching current hashes, exactly one target need, and a hash proving that the retained
text is the complete previously captured input. Replay preserves evidence IDs and
retrieval times. Abbreviated, native-record or RSS contexts without that proof are
not silently reconstructed as complete public pages; the limitation is explicit.

Acquisition remains inside the same PostgreSQL question job. Each owned DNS/HTTP/
parse operation runs in a killable child process under the question's hard deadline
and a 512 MiB address-space cap. Only bounded network/parser results cross this
boundary: reservations, lease checks and canonical writes remain in the parent.
This introduces no new scheduler, job framework or persistence layer.

Direct public HTML/text and text-extractable PDFs must fit the whole-input limits:
750,000 wire bytes, 30,000 extracted characters and, for PDF, 20 pages. Oversized,
encrypted or partly unextractable/scanned PDFs are rejected, not truncated; no OCR
or PDF metadata-derived publication date is claimed. A successful public page that
explicitly requires JavaScript rendering may use configured Firecrawl extraction,
with a separate request/document debit and cost reservation. An HTTP error, login,
CAPTCHA, access denial, redirect or restriction does not authorize that fallback.
Search snippets remain discovery hints; extracted text still faces normal admission.

Structured authoritative records retain source-specific interpretation. Public news
uses the normal supplemental path. A public page hosted on an exact hostname
already present in the validated source registry can be considered for supplemental
admission; a government-like hostname or `.gov` suffix alone grants no authority.
It remains supplemental and cannot impersonate a native adapter record or positively
qualify a need. A narrowly admitted relationship-only page must
match the exact project, the explicitly extracted organization's hostname and title,
and a contact-only rejection from normal activity parsing. Mixed adverse/supply
pages cannot use that exception. Relationship assessments omit activity and power
fields; they cannot qualify a need. Explicit AI-generated/directory summaries are
quarantined before normal news interpretation. Project assignment, role, authority
and reachable contact remain separately extracted concepts.

The question about a temporary-power requirement is deliberately separate from
supply adequacy. A cited temporary-service scope does not establish generator demand,
utility shortage or unresolved commercial need. Construction does not establish
commissioning. Research never assigns a commercial disposition or qualification tier.
Inactive/no-longer-supported and confirmed below-floor targets remain reevaluable
through the deterministic commercial evaluator even after they disappear from the
ordinary opportunity list.

Typed public reports now enter the existing Interpretation/Evidence model as
`project_research_supplement` (`project-research-claims-v2`). Exact grammatical
project/site subjects, affirmative activity predicates and explicit date provenance
are required. Current conflicting sources remain CONFLICT; neither the latest URL nor
a model settles them. Corrections preserve historical evidence. Typed phase, permanent
service, activity supply, load and timing answers can resolve questions independently
of qualification. Energization alone does not establish adequate supply. Public load
reports do not write qualified MW. Supported closure, pause, adequate supply and
conflicts conservatively constrain commercial action and existing qualification.

The existing PRD Prospect/Lead criteria now have a narrow deterministic official-permit
implementation. It replays accepted native address/description evidence, requires
separate exact-site/activity demand and unsuitable supply for Prospect, and requires
MW/start/duration ranges, one explicit aggregate suitable-supply interval covering
the full start window and duration, and a supported buying role for Lead. The supply
can be zero or nonzero; component supplies are not summed or assumed suitable.
For required range [Dmin, Dmax] and suitable supply [Smin, Smax], the conservative
remaining range is [max(0, Dmin − Smax), max(0, Dmax − Smin)]. Effective Lead visibility
uses that remaining range against the inclusive 300 kW floor, while retaining the
gross required load separately. A range crossing the floor remains uncertain.
Hypothetical, historical, conditional, quoted,
ambiguous or conflicting statements cannot qualify. Read-only API replay caps aged-out
Lead fields without rewriting historical evidence; canonical updates clear obsolete
qualification fields. This adds implementation of the existing gates, not model
qualification or a commercial-state shortcut.

The hourly scheduler reprojects saved targets in one bulk pass, including targets
outside the live 50-card shortlist. Fresh unchanged answers do not create more jobs;
identity, buying-chain and material state changes are included in semantic hashes.
Source registry definitions, selected source sets and current research policy also
participate in reuse. Daily acquisition and active-blocker caps remain independent
of this read-only projection. Registered disabled collectors are not acquired;
individual `research-public-*` pages intentionally remain nonpolling source records
and are eligible for bounded targeted refresh.

The morning view counts unique saved evaluation versions correlated with research,
not repeated question receipts. It shows separate tier changes, new evidence, reason,
next action and read-only history. Concurrent operator contributions are not falsely
attributed solely to research. The shared metrics/validation tools preserve this
same distinction and require explicit corpus provenance and immutable baselines.

Known bounds: exact native GET routes cover Austin, Chicago, Seattle, Boston,
El Paso and Federal Register stable identifiers. Other registered families can use
retained facts and eligible public supplements, but do not acquire unimplemented
native adapters by inference. RRC's form-based download is excluded; Houston/Dallas
bulk workbooks and Georgia/NC/Taylor/MA sources have no exact native research route
in this slice. Public PDF support does not change that native-source distinction.
Strict subject/activity/date/relationship and qualification grammars intentionally
leave unsupported wording, complex supply schedules and incomplete inputs unknown. The original PR23 corpus and provider configuration remain unavailable here;
local fixture proof is not retained-corpus or production proof. See the
[validation report](../validation/gl3-029-autonomous-pursuit-research.md).
