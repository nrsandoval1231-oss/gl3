# TITLE-02 independent acceptance review

**Verdict: FAIL / hold release on this candidate.** Reviewed the uncommitted `gl3-title-enrichment` application diff against `.agent/packets/TITLE-02.md` on base `b97de9b`. The feature remains disabled by default and no provider call is implicit on GET. The OpenAI request is bounded to 8,000 input-payload bytes and 240 output tokens, uses the separately allowlisted `POWER_NEED_TITLE` contract and shared logical-call ledger, and stores title versions apart from canonical project/need facts and question briefs. Model mismatch and output-usage overrun route through existing quarantine. Source/need/input freshness is checked on request, before dispatch intent, and before accepting a result. I found the following concrete blockers.

1. **Batch projection adds one database query per need (performance / acceptance).** `app.py:3832-3848` invokes `title_preview` for each detail. `titles.py:85-107,324-335` calls `_assert_evidence_sources_enabled`, which executes a new `Source`/`Observation`/`Evidence` SELECT (`titles.py:43-64`) for every need. The caller already has batched links and sources. This is a new N+1 in both detail projection and saved-browse rebuild (`saved_browse.py:180-200`) and conflicts with the packet's batch/no-N+1 requirement. Use the supplied source map and linked evidence, or batch the source-state check once, and verify query count grows by batches rather than records.

2. **A completed, unusable response can be misclassified as dispatch-unknown (ledger / operations).** `titles.py:439-450` calls `call_openai_request`, then raises plain `ValueError("provider_incomplete")` inside the `perform_legacy_call` invocation if `incomplete_details` is present. That exception lacks the provider response metadata used to record a conclusive failure, so `legacy_calls.py` can retain `SENT_OUTCOME_UNKNOWN` and its active budget reservation despite receiving a response. The adapter already raises a conclusive `ProviderResponseError` for a non-completed response; any additional incomplete check should occur after ledger completion or carry the adapter's conclusive response evidence. Test the status/usage/ledger receipt for this branch.

3. **A displayed title can truncate an exact source quote (factual fidelity).** `_activity_options` admits a 180-character complete line, while `validate_title` concatenates a project name, organization, role and line, then returns `title[:240]` (`titles.py:104-119,229-276`). With long supported names the cut can remove a late negation or condition from the displayed activity even though the citation still contains it. This violates the stated complete-quote and negation rule. Omit an optional component or fall back to the deterministic title when the complete assembled title exceeds the display bound; test a long cited line ending in a qualifier.

4. **The required PostgreSQL acceptance path is not tested.** `backend/tests/unit/test_power_need_titles.py` has six useful offline cases for option IDs, role preference, request bound and overrun quarantine. New web tests cover explicit action, polling/readback and a late status from a switched need. There is no new integration test for authenticated queue to mocked provider to persisted current title and saved list/detail, duplicate/cached request, source disabled or changed before/during dispatch, lost fence/unknown outcome, or disabled default. These paths involve real transaction and job-fence behavior; unit and mocked-browser tests cannot close the gate. Root's full PostgreSQL suite and UI harness were still running at review time, so I do not certify them.

The first and final `title_input` calls in `process_title_job` sit outside its inner try (`titles.py:410-420,512-517`). Normal `worker.run_one` catches their exceptions and marks a still-pending title failed (`worker.py:866-889`), so this is **not** a normal-worker orphan-pending finding. The worker result remains advisory; the code does not change tier, rank, accepted facts, project name, MW, or supply. List search and sort receive the ready title through the saved generation; stale/failed/pending states use deterministic fallback. Review these conclusions again after fixes and PostgreSQL evidence; no source edits, provider calls, or production actions were made in this review.
