Initial review of the superseded script (findings retained for traceability):

1. **High — the inactive-title policy is asserted in the gate file but not enforced on the running services** (`title02-rollout.py:20,95-103,181-186,263-265`). The new application reads `POWER_NEED_TITLES_ENABLED` (default false in `backend/src/gridlens/settings.py:134`), and title endpoints/worker branch on it (`api/app.py:4112`, `intelligence/titles.py:387,438`). `controls()` omits that variable, so its pre/post equality can pass if the existing compose/runtime happens to supply `POWER_NEED_TITLES_ENABLED=true`; the old API would have ignored it, and the new API would activate titles despite `new_contract_activation=False`. The separate contract allowlist check prevents the title inference contract as currently parsed, but it does not enforce the requested disabled surface. Minimal repair: require the live pre-cutover API/worker/browse title flag to be absent or false, include it in the control comparison, and verify the newly started services report false. Keep the gate-file assertion.

2. **High — the worker drain can call an expired-lease job idle while its process still performs work** (`title02-rollout.py:181,204-230`). Both checks count only `status='running' AND lease_until>now()`. The queue re-leases expired running rows (`backend/src/gridlens/jobs/queue.py:155-181`), while the worker may still be processing a previously leased job; its lease is 600 seconds (`jobs/worker.py:701`). A long or stalled external I/O can therefore be in progress with a running row whose lease has expired. The `SHARE` lock blocks new DB lease writes, but cannot fence that in-process I/O, and `docker stop --timeout 15` can kill it. The logical-call-status query is taken before the drain, not inside it. Minimal repair: under the drain lock, require no `running` jobs regardless of expiry (and recheck unresolved logical calls while fenced), or provide an independently proven process-idle condition for expired rows before stop. Treat stale expired rows as a blocked cutover needing reconciliation, not as evidence of idleness.

3. **Medium — isolated-DB stop failure suppresses the final receipt** (`title02-rollout.py:275-280`). `run(docker stop …)` can raise in `finally` before `test_database_stopped` and receipt writing. This leaves the exact production outcome unrecorded, including the case where candidate rollout succeeded but cleanup failed. Catch and record the stop/inspect outcome, always write the receipt, and mark the rollout non-passing or requiring operator attention if isolated PG remains running. Also inspect/stop it when `docker start` returns failure after partially starting (`:221-223`).

Positive checks in the script: pinned old/new image IDs and image revision, exact old compose/startup/runtime hashes, compare-and-restore of selected controls and credentials, canonical-table checks before/after migration and browse rebuild, fresh dump with isolated restore verification, and rollback that stops/inspects all three policy writers before old-image rebuild. The migration is additive and rollback intentionally retains it. Those checks are useful but do not close the above cutover gaps.
