# Pursuit Workspace interaction contract

Owner-approved October 20, 2026; the v3 execution-first layout is specified in [UI_CANON](UI_CANON.md). Existing engine, API authentication, power-need identity, qualification, and workflows remain authoritative.

Keep the supported horizontal Opportunities, Research, Signals, and Operations navigation, search, and account controls. Apply the v3 visual treatment to these existing destinations. The prototype's Saved navigation is illustrative and does not introduce a production Saved page. Opportunities remains a prioritized queue of individual power needs, with a contextual brief. Signals remains the entry to a shared grouped-source evidence browse, defaulting to Signal with a local qualification selector for Signal, Prospect, and Lead. Preserve grouped conservative physical-project members, source context, group/cohort counts, SHOW/REVIEW/HOLD decisions, qualification-scoped CSV, and advanced geography, industry, activity, timing, known-MW, priority, and workflow-status filters. Keep group counts distinct from individual need counts. On Opportunities, the compact Daily Briefing exposes real Action now/Research/Watch disposition counts and the existing persisted material-change review workflow. Do not invent follow-up or open-question counters. Phone selection opens focused detail and Back restores queue state.

Queue controls include disposition, qualification, search, and supported sorting. Search and all cohort counts must reflect the full available cohort, not only the rendered page. Keep priority, Action now/Research/Watch/Reject disposition, pursuit status, and Signal/Prospect/Lead qualification independent. Show activity-specific identity and next action.

Detail prioritizes a supported next action, then need/supply/gap/timing facts with provenance, missing evidence, and expandable sources. Unknown supply never yields a numeric gap. Prepare-action reveals questions and does not record contact. Actions enter existing workflows and retain their own validation and persisted readback for supported facts, notes, status, follow-ups, and history; no generic prototype form is prescribed. Updates do not promote qualification or change disposition automatically.

The standalone prototype uses fictional records, an illustrative Saved destination, and browser-tab-local persistence. It demonstrates visual direction and interaction only. Local production-code checks and runtime proof are distinct from live production deployment and acceptance. The applicable gates separately verify authenticated persisted records, correct project/need/pursuit identity, refresh/readback, desktop/mobile behavior, evidence and qualification invariants. UI approval does not close the parent Finish Contract or authorize deployment.
