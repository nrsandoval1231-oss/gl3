The CSV therefore labels package presence as observed, while application-level call-path reachability and exploitability remain UNKNOWN. Debian/Alpine base libraries in runtime targets are present in the image; that alone does not prove an exploitable path. ## Row-level reachability and advisory review

The CSV now carries `RuntimeReachability`, `ReachabilityEvidence`, and `Disposition` on every observed occurrence. The disposition vocabulary is deliberately conservative: `SUPPORTED_FIX_AVAILABLE_IN_REPORTED_PACKAGE_REPOSITORY` means Trivy's own `FixedVersion` field identifies an upgrade for that archived occurrence; `UNKNOWN_*` means the evidence does not establish both a safe supported remediation and the advisory's runtime preconditions. Fixed metadata is not a claim that a repair was applied or that the candidate passed a rescan. No row is assigned a mitigation disposition because no row-specific mitigation was verified.

Evidence from the controller's sanitized `.artifacts/hardening-20261024/production-libraries.json` shows:

- API `uvicorn` maps `/usr/lib/x86_64-linux-gnu/libssl.so.3`, `libcrypto.so.3`, `libuuid.so.1.3.0`, Python `_ssl`, and `pyexpat`. Thus those components are runtime loaded; the report does not trace vulnerable symbols or establish exploit trigger conditions. This is the archived production API scan, not the separate final API image.
- The PostgreSQL process `ldd` output includes `libxml2.so.2`, `libssl.so.3`, `libcrypto.so.3`, and `libsystemd.so.0`. PostgreSQL 18's official documentation says XML type input and `XMLPARSE` require a build with `--with-libxml`, and accepts SQL forms such as `'<foo/>'::xml`. The PostgreSQL binary's link is direct evidence of the dependency. CVE-2026-6653 specifically names `xmlParseInternalSubset` and malicious XML; this path is plausible from SQL XML input and is not classified unreachable. Actual attacker privileges and whether the offending DTD/entity condition can reach this exact vulnerable parser code are UNKNOWN. The Debian tracker reports the installed Trixie version `2.12.7+dfsg+really2.9.14-2.1+deb13u3` vulnerable, with no Trixie fix listed (fixed only in unstable at `2.14.5+dfsg-0.1`).
- PostgreSQL's libxml2 rows for XPointer, XInclude, dictionary, URI escape, and callback functions are marked conditional/unknown because the library is loaded, but no symbol-level trace or exact server feature call was collected. CVE-2026-74860 requires Python SAX bindings; the probe shows no Python process or Python library mapping for the DB service, but that is not proof the bindings are absent from the image, so the row remains UNKNOWN.
- The web `nginx` process is active and maps `libpcre2-8.so.0`, `libssl.so.3`, and `libcrypto.so.3`. Its checked-in config only listens on HTTP 8080 and uses core proxy/static directives. Therefore nginx and PCRE2 request parsing are reachable components; individual CVE triggers remain tied to the per-row Trivy description. OpenSSL is loaded, but no TLS listener or HTTPS upstream appears in the config; TLS-specific trigger reachability is conditional and UNKNOWN. The web findings are from the archived image; the final web artifact is clear of HIGH/CRITICAL findings.
- util-linux, mount, and related Debian packages appear in image inventory, but no API startup command invokes `mount` or `nsenter`. The compose file does not request `privileged` or extra capabilities. The sanitized probe did not capture effective capabilities, SUID bits, or host fstab state, so mount-related CVEs stay UNKNOWN rather than being called unreachable. Debian's tracker currently marks Trixie's `util-linux 2.41.5-0+deb13u1` vulnerable for CVE-2026-76642 and CVE-2026-78408/09/10; fixed versions are listed in unstable (2.42.3/2.42.4), not the installed Trixie release. Do not pull an unstable package into this image without a separately reviewed compatibility plan.
- For gosu, the PostgreSQL 18.6 upstream Dockerfile sets `GOSU_VERSION=1.19`; the running database probe shows no active gosu process, consistent with the entrypoint helper exiting after switching identity. The exact extracted binary is SHA-256 `52c8749d0142edd234e9d6bd5237dff2d81e71f43537e2f4f66f75dd4b243dd0` (1,769,900 bytes), and `govulncheck v1.9.0` ran in binary mode at symbol level against it using vulnerability DB last modified `2026-10-21T00:27:29Z`. The stream reports 3 symbol findings and exits 0 even when findings exist. Those three reachable findings are all GO-2026-6686 / CVE-2026-61801 in `github.com/moby/sys/user` v0.1.0, fixed upstream in v0.4.1: `GetExecUser`, `GetExecUserPath`, and `ParseGroupFilter`. The advisory describes unbounded parsing of passwd/group data that can cause denial of service. This is a positive exact-binary match and requires owner/vendor risk disposition; it is not a blanket clearance nor a proof of attacker reachability. The 26 Trivy stdlib rows remain unknown for their individual CVEs: the binary scan does not find vulnerable stdlib symbols in gosu, but it analyzes only those symbols tracked by govulncheck and does not map those 26 Trivy CVEs one-to-one. In particular, a clean exit code is not evidence of no findings. Preserve advisory matching and exact binary scope when interpreting the result. No custom gosu rebuild is recommended from this scan alone. The archived image context shows the PostgreSQL entrypoint helper runs as root to set up/chown the data directory and switch to the postgres identity; the process probe itself shows no current gosu execution. Read-only production evidence shows `/etc/passwd` and `/etc/group` are root-owned mode 0644, PostgreSQL processes run as UID 999, and no passwd/group bind mount exists; only the database data volume is writable, while the initdb bind is read-only. This reduces the evident path for an untrusted database process to modify those files, but does not erase the exact-binary symbol match or establish all host/container threat paths. The API process runs as UID 0, which remains a separate risk.
