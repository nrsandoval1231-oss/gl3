## Read availability during ingestion (2026-11-11, owner-approved, off by default)

Account and project result routes normally answer `503 Qualification pending` whenever a canonical write is newer than the published browse generation. With `BROWSE_SERVE_STALE=true` on the API, those reads instead return the last complete generation with `refresh_state: "updating"` and its `as_of` time, and the UI labels the snapshot. Only project-scoped writes qualify: policy changes, clock expiry, writes that advance the full-scope revision (source policy, editorial, unscoped) and company identity, identifier, membership or identity-link writes and need or project deletions (tracked by `browse_state.structural_revision`, schema 0053) still return pending. A generation built more than `BROWSE_STALE_MAX_SECONDS` (default 1800) ago is not served; that bound measures build age, not time spent stale, so after a quiet period the first write can still return pending. Several auxiliary reads (demand summary, account identity, pursuit workspace, signal counts) also use the stale generation without an `updating` marker. Do not enable the flag in production until these are resolved or accepted by the owner. Builders, maintenance and explicit evaluation instants always use the strict rule. This setting is implemented and tested locally only; it is not enabled or verified in production.

The `deploy/digitalocean` compose proposal now starts `API_WORKERS` API processes (default 2), each with its own database pool of up to 15 connections; the protected host compose file is separate and unchanged. Schema `0052_ingestion_lookup_indexes` adds six lookup indexes concurrently and `0053_browse_structural_fence` adds the identity fence column and triggers; nginx compresses text responses and caches fingerprinted `/assets/` files. The nginx configuration passed `nginx -t` and a local header check (index no-cache, assets one year plus gzip, framing headers inherited) with nginx 1.24; it was not run in the Alpine web image.
