## Read availability during ingestion (2026-11-11, owner-approved, off by default)

Account and project result routes normally answer `503 Qualification pending` whenever a canonical write is newer than the published browse generation. With `BROWSE_SERVE_STALE=true` on the API, those reads instead return the last complete generation with `refresh_state: "updating"` and its `as_of` time, and the UI labels the snapshot. Only project-scoped writes qualify: policy changes, clock expiry, writes that advance the full-scope revision (source policy, editorial, unscoped) and company identity, identifier, membership or identity-link writes and need or project deletions (tracked by `browse_state.structural_revision`, schema 0053; all of these report as the `full_scope` reason) still return pending. The snapshot is served only while it has been stale for at most `BROWSE_STALE_MAX_SECONDS` (default 1800). `browse_state.stale_since` (schema 0054) records when the published generation first fell behind: it is set by the first write after a publication, is not moved by later writes, and is cleared when a generation that covers the current revision is published or promoted. A snapshot built hours ago is therefore still served at the start of an ingestion run. A NULL `stale_since` while the state is behind (for example a state that was already behind when 0054 was applied) is pending until the next publication, never servable. Only the routes that return `refresh_state` (account groups, group projects, group open and the project page) may serve the snapshot; every other read (Companies, search, demand summary, account identity, pursuit workspace, signal counts, builders and maintenance) stays strict and answers pending. The fence also closes on need deactivation (`power_needs.active` cleared), which is how ingestion retracts support, and on routine identity or membership churn, so the setting may engage less often than the raw scoped-write rate suggests. Each read on the four routes (`groups`, `group_projects`, `group_open`, `projects`) and on the strict user-facing readers is counted as `current`, `updating` or `pending`; a pending read carries one reason from a closed set: `policy`, `clock`, `full_scope`, `stale_age`, `no_generation`, `flag_off` (the snapshot was servable but the flag is off) and `strict_reader` (servable but the caller does not opt in). Hard fences are reported before those two modes, and `no_generation` also covers a publication landing between the read and its diagnosis, so it can appear while a generation exists. Counting costs no query on the `current` path; the pending path adds one read of `browse_state`. While the flag is on the API writes one line per counted read (including `current`, so expect a line per read) to the `gridlens.intelligence.saved_browse.reads` logger (stderr): `browse_read route=<route> outcome=<outcome> reason=<reason|-> generation=<uuid|->`, with no request parameters, search terms, names or contact data. Count them after an ingestion cycle on a non-production copy, for example `grep -o 'route=[a-z_]* outcome=[a-z]* reason=[a-z_-]*' api.log | sort | uniq -c`; `saved_browse.read_counts()` returns the same tally for one process.

Dated local measurement (2026-11-11; synthetic rollup-scale corpus plus the real ingestion code on fixture payloads; one run per mode of about 110 reads at roughly 8 per second; not production traffic): during one mixed ingestion cycle with the flag on, 61% of reads were `current`, 18% `updating` and 19% `pending` (all `full_scope`; longest continuous pending window 3.1 s). With the flag off the same cycle gave 56% `current` and 40% `pending` (26 `flag_off`, 20 `full_scope`; longest window 3.3 s), so the flag converted its `flag_off` pendings to `updating` and left the `full_scope` ones. By event class with the flag on: new Austin permits 59% `updating`; amendments 33% `updating`; new RRC permits (each inserts an operator membership) 0% `updating`, 23% `pending`; support lost (need deactivated) 53% `pending`; unchanged replays wrote nothing and every read was `current`. The `full_scope` fence therefore removes most of the benefit for new oil and gas permits and for deactivations. Builders, maintenance and explicit evaluation instants always use the strict rule. This setting is implemented and tested locally only; it is not enabled or verified in production.

## Ingestion batch commits (performance Phase 2 Step 3, 2026-11-11)

`INGESTION_BATCH_SIZE` (default 1, which is off; 1 to 10000) and `INGESTION_BATCH_MAX_SECONDS` (default 2.0, up to 30) set how `process_records` commits for every source that is not a structured collection segment (publisher RSS keeps its own loop). With a size above 1 the worker holds one transaction open per batch: each durable boundary inside a record becomes a SAVEPOINT boundary, and the real COMMIT, the fence check, the `job.checkpoint` write (the last fully processed record) and the lease extension happen once per batch, after the batch size or the time bound is reached, whichever comes first. A value of 1 commits at every boundary exactly as before; `commit=False` callers are unchanged. Consequences to know before raising the size: row locks taken while processing a record (projects, needs, observations, interpretations, advisory locks) are held until the batch commit, so a concurrent API write that references a locked project or need can wait up to the time bound (see `experience/benchmarks.md`); a crash loses only the uncommitted batch and replays idempotently from the committed checkpoint; lease loss rolls back the whole uncommitted batch; any other exception rolls back only the open savepoint segment and then commits the released work if the lease is still held. Records that fetch a companion PDF end the batch first and commit the rest of that record normally. Local measurements only; nothing here is enabled or verified in production. It ships off because the measured gain is limited to replays (unchanged records 1.4 to 1.8 times faster; all-new ingestion unchanged) while pursuit, owner-fact and need-status inserts that reference a project or need in the open batch wait until it ends (lock-scope test `test_open_ingestion_batch_does_not_block_api_style_writes`); do not raise it until those locks are narrowed to `FOR NO KEY UPDATE` (proposed patch: `experience/benchmarks/step3-lock-narrowing.patch`) and the `browse_state` lock no longer spans a batch.
