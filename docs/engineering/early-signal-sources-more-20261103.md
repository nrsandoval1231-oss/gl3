This is the second part of section 4 ("Early-signal layer") of the [ingestion handoff](../strategy/ingestion-handoff-20261103.md); the first part (ERCOT planning, PUCT certificate dockets, links) is [workstream 4a](early-signal-sources-20261103.md). The same stage discipline applies (shared pacer, typed `DocumentFailure`, validators, report, rest-until-`not_before`). **Everything ships off.** No deployment, credential, paid provider, migration or production data was touched. The live checks below are one-off reads, not evidence that anything works in production.

Rules held throughout: evidence or nothing (hash, page and verbatim quote with every value); unknown is never zero; a stated figure is a stated figure (never inferred, never site demand); documented / calculated / estimated / inferred / unknown stay distinct (no value here is `estimated` or `inferred`); at most one request per second with the declared generic user agent; no untrusted response text in any failure code, exception or index; `first_seen_at` is never rewritten; **evidence only**: no retrieval method here is in any signal-admission set, so enabling a source creates no project, need or card (tested).

## Design

All four sources reuse `early_signal_http.EarlyFetcher` (exact host and path policy, pinned public DNS, no redirects, Content-Length and running-count caps, media-type check, declared user agent, shared pacer) and, where a document stage exists, `early_signal_stage` (conditional GET only with a stored state, hash change detection, changed bytes keep `first_seen_at` and list `replaced_sha256`, 429/503 stop the stage and store `not_before`, permanent failures remembered, environment failures backed off, listing-shrink notice). `early_signal_more.py` holds only the shared pieces: a typed listing fetch (a listing 429 carries `acquisition_code` and `Retry-After` for the worker), a small HTML table parser, quote-bound evidence values and the generic stage runner. The service routes the new retrieval methods through the existing early-signal stage hook; the registry validates each source's exact query shape.

### Comptroller registry (`texas-comptroller-dc-registry`, no document stage)

One request per run (weekly cadence). Each registry row is one observation `TXCOMP-<DC|LD######>`; the row text is the evidence, so a changed row (a new operator, an exemption end date) is a **new evidence version and the earlier one stays**; an unchanged re-run is idempotent. A row with no registration number, or with two different roots, is skipped and counted. A row that omits the trailing exemption-end cell has an end date of "not listed". `publication_date` is empty: the effective date is when the registration took effect, kept as `event_date` with the label "registration effective", never as the time the page listed it. A page with no recognisable rows is a loud `SourceParseError`, never "nothing registered". Absence from a later page is not recorded as a removal. The abstract says in words that there is no county, address or MW.

### OCC notices (`oklahoma-occ-data-center-notices`)

Listing: one request for the page; the links under the "Notice of Intent Submissions" heading (exact PDF directory policy) become records whose link text gives company, optional project, county and date, each re-derived from the label only when it matches the expected shape (otherwise unknown). The listing record stands on its own (an official list entry is evidence), so it is kept even with the document stage off. Stage: the PDF's first two pages are matched for four label/value pairs (company, land purchase date, county, planned utility provider); each value is kept only if the same pattern run on its own quote returns it. The attestant, the adjacent landowners and every attachment are never read into a field or stored (tested). A scanned form is an abstention (`empty_text_layer`), remembered as a permanent failure until the bytes change; the listing record remains. A notice states a land purchase, not a load: no MW. 20 MB cap (observed 6 to 7 MB scans).

### County agendas (`texas-county-abatement-agendas`, pilot: Haskell)

Listing: one request for the Commissioners Court page, agenda PDFs on the exact `/upload/page/7690/` path, newest meeting first, cancellations skipped, `.doc` agendas not listed, at most `max_agendas`. The meeting date comes from the link label. An agenda is split into numbered items; an item is kept only if it names a **tax abatement, abatement agreement, Chapter 312, reinvestment zone, data center or large load** (so "abatement of neighborhood nuisances" is not matched). Each item is a verbatim slice of the page with page and span. Inside an item, the entity (only after "agreement/abatement/application with ..." or "between ... County and ..." and ending in a company suffix), a dollar investment (million/billion are `calculated`), a stated MW (GW is `calculated`), an acreage and a stated location are kept only when the same pattern run on their own quote returns the same value; **two different amounts of one kind in one item are a conflict and stay unknown** (no value is chosen). An agenda item is a topic for discussion or action, not an approval, an investment or a load. A scan is withheld (not stored empty); with the document stage off the whole source stores nothing (a bare agenda link is not evidence of an abatement). An agenda with no match stores "not a statement that none was discussed". Only one county is implemented; `counties` must equal `["haskell"]`.

### TCEQ water-right applications (`texas-tceq-water-rights-pending`)

Listing: one request (weekly cadence); one observation per WR number (`TCEQWR-<no>`) with applicant, county and the five dates as listed. The row hash covers every listed field and file name, so a new "administratively complete" or notice date is a new evidence version. `publication_date` is the notice-issued date, `event_date` the received date. The listing states no volume or use; the abstract says so. Stage: for rows with a notice package, the first four pages' text is searched for acre-feet figures; each is kept with a verbatim quote and a deterministic role (`requested`, `existing_authorization` or `stated`, from the verbs in the quote), up to eight; **figures are never summed and never converted to a demand**. The applicant's name is kept with its quote when the notice names it; purposes are the stated words (municipal, industrial, mining, ...); a data-center mention is recorded only if the text says so. 40 MB cap; `max_downloads` 2 by default.

## Limits and risks

- Registry rows have no county or MW; they are entity keys and a discovery signal. Absence from a later page is not a removal.
- OCC lists only what the OCC chooses to list; two of three forms are scans (no OCR here), so for those only the link text (company, county, date) is known, not the land purchase date.
- Haskell agendas: roughly half are scans, two are `.doc`; one county only. Item-level fields are rarely stated on an agenda; the executed abatement agreements linked from `/page/haskell.Abatement` (investment, location) are not read.
- Milam would need an exception to the no-redirect rule for a named third-party host; Medina is blocked by a `robots.txt`. Neither is attempted.
- Water: the listing carries no use. No row names a data center today. Notice packages are very large; only the first four pages are read, within `max_downloads` per run and a 40 MB cap.
- The Windows host has no address-space cap for the reading child; POSIX children are capped.
- Site-policy pages for `tceq.texas.gov`, `comptroller.texas.gov`, `oklahoma.gov` and the county site were not read for terms of use beyond `robots.txt`; the owner should confirm before enabling.
- No evidence here shows production retrieval, scheduled cycles, lead time or source breadth.
